# Troubleshooting & Monitoring

This guide is for after the plugin has been deployed and is in day-to-day use. If a
user reports "it's not working" and you don't know why, start here.

It covers all three deployment options, but most of the depth is on **Option C (M365
Copilot)** since that is the recommended, org-wide deployment and the hardest one to
observe — there is no local console or log file to tail.

---

## Quick triage checklist

Before digging into logs, rule out the common causes in order:

1. **Is the plugin enabled?** Microsoft 365 Copilot → **Sources & Skills** (or
   **Get agents**) → confirm **BPA Analytics** appears and is toggled on for the affected
   user.
2. **Has the user consented?** OAuthPluginVault (Option C) requires each user to
   consent once via the OAuth flow on first use. If they never saw or dismissed the
   consent prompt, every call will fail silently from their point of view.
3. **Is the OAuth registration still valid?** See
   [OAuth registration issues](#oauth-registration-issues) below — an expired or
   deleted Teams Developer Portal registration is the single most common cause of a
   tenant-wide outage that "used to work."
4. **Is `mcpServerUrl` correct?** Check `manifest.json` still has the real Power
   Platform environment ID (not `YOUR_ENVIRONMENT_ID`) and matches
   `https://agent365.svc.cloud.microsoft/mcp/environments/{environmentId}/servers/msdyn_ERPAnalyticsMCPServer`.
5. **Does the user actually have BPA access?** OAuthPluginVault only proves identity —
   the **BPA User** role (and underlying D365 Finance access) is still enforced
   separately. A user without that role will get empty or denied results, not a
   plugin error.
6. **Reproduce with a minimal prompt.** Ask the affected user (or reproduce yourself)
   with: `"Show me the BPA dataset schema."` This exercises `get_bpa_dataset_schema`
   with no other skill logic involved, isolating connectivity/auth problems from
   skill-routing problems.

## "Authentication is still processing. Please try again."

This message is generated by Microsoft 365 Copilot's OAuth consent flow (the
`OAuthPluginVault` handshake with `agent365.svc.cloud.microsoft`), not by any code in
this repository — there is nothing to "fix" in the plugin itself, but it can be
diagnosed:

1. **Understand what the message means.** It typically appears when the OAuth
   consent/token exchange hasn't completed yet — either the user dismissed or never
   finished the consent prompt, or Copilot is waiting on a token that never arrived.
2. **Confirm the deployment option in use** (per [README.md — Deployment
   options](README.md#deployment-options) and `manifest.json`). If this is **Option C**
   (M365 Copilot with `OAuthPluginVault`), the checklist below applies. If it's
   **Option B** (local MCP/VS Code), the cause is different — see [Sign-in
   issues](#option-b--local-mcp-vs-code).
3. **Follow the [Quick triage checklist](#quick-triage-checklist) above**, in
   particular:
   - Confirm the plugin is enabled for the user (**Sources & Skills** / **Get agents**).
   - Confirm the user actually completed the one-time OAuth consent prompt — don't just
     dismiss it, go through it fully.
   - Check whether the Teams Developer Portal OAuth registration is still active — see
     [OAuth registration issues](#oauth-registration-issues) below; this is the most
     common cause of "auth-shaped" failures that look stuck/silent.
   - Verify `manifest.json`'s `mcpServerUrl` matches the real environment ID and
     `authorization.type` is `OAuthPluginVault`.
4. **Check [Entra ID sign-in logs](#entra-id-sign-in-logs-the-closest-thing-to-a-request-log)**
   (**Identity** → **Monitoring & health** → **Sign-in logs**) for `Failure` entries
   with an AADSTS error code around the time of the failure — this shows whether the
   consent/token request is failing, being blocked by Conditional Access, or
   genuinely stuck.
5. **Reproduce with a minimal prompt** (e.g., `"Show me the BPA dataset schema."`) to
   isolate whether this is a general auth failure vs. a skill-specific issue.
6. **If unresolved**, use the [Escalation checklist](#escalation-checklist) below to
   gather: deployment option, exact prompt/error text, timestamp, affected users,
   sign-in log entry, OAuth registration status, and `manifest.json` settings — then
   escalate to Microsoft 365 support, Power Platform support, or the plugin maintainer.

## Option C — M365 Copilot (recommended, org-wide)

This is the deployment most teams run, and the one where "we don't know why it failed"
is most likely to come up, because there is no local terminal or log file — everything
happens inside Microsoft 365 and Entra ID (Azure AD).

### Where to look

| Symptom | Where to check | What to look for |
|---|---|---|
| Plugin missing from Sources & Skills | M365 Admin Centre → **Agents** → **All agents** | Plugin present, status = published, not disabled/blocked by a Copilot policy |
| "I don't have a way to connect to BPA from here" | `manifest.json` → `authorization.type` | Must be `OAuthPluginVault`, not `None` — see [README Step 6](README.md#6-first-use--authentication) |
| Auth works for some users, not others | Entra ID → **Enterprise applications** / **Sign-in logs** | Confirm the user's account isn't blocked by Conditional Access, MFA, or app assignment scope |
| Everyone suddenly fails at once | Teams Developer Portal → **Connectors** → **OAuth registrations** | Confirm the registration used in `manifest.json → referenceId` still exists and hasn't been deleted or replaced — see [OAuth registration issues](#oauth-registration-issues) |
| Auth succeeds, BPA calls fail or return empty | Power Platform Admin Center → environment → **Security roles** | Confirm the signed-in user has the **BPA User** role (and D365 Finance Basic User) — see [SECURITY.md](SECURITY.md#required-permissions-least-privilege) |
| Intermittent failures / timeouts | Entra ID **Sign-in logs**, filtered to the app used by the OAuth registration | Look for `interrupted` or throttling (HTTP 429) entries around the failure time |
| Plugin responds but with the wrong data / stale skill behaviour | `manifest.json` `version` vs. what's actually installed | Confirm the tenant was updated (**Agents → All agents → BPA Analytics → Update**) after the last skill change, per [Updating the plugin](README.md#7-updating-the-plugin) |

### Entra ID sign-in logs (the closest thing to a "request log")

Because `agent365.svc.cloud.microsoft` sits behind Azure AD, every OAuth token
exchange for the environment's app used by the Teams Developer Portal registration
(see [README Step 2](README.md#2-register-the-oauth-connection-teams-developer-portal))
shows up in Entra ID:

1. [entra.microsoft.com](https://entra.microsoft.com) → **Identity** → **Monitoring &
   health** → **Sign-in logs**.
2. Filter **Application** to the app tied to your OAuth registration.
3. Look at the **Status** column — `Failure` entries include an error code
   (e.g. `AADSTS65001` = user or admin hasn't consented, `AADSTS700016` = app not found
   in tenant, `AADSTS50076` = MFA required and not satisfied).
4. Click a failed sign-in to see the **Conditional Access** tab — this shows if a
   Conditional Access policy blocked the request before it ever reached the BPA MCP
   server.

This is the primary signal for "auth-shaped" failures (the plugin can't connect at
all, regardless of what the user asked).

### OAuth registration issues

Unlike some MCP connectors, this plugin's `OAuthPluginVault` does not depend on a
client secret you manage — the Teams Developer Portal registration points at your
tenant's existing OAuth token endpoint (`login.microsoftonline.com/{tenantId}`) with
the `https://service.powerapps.com/.default` scope, so there's no secret to expire.
What can still break it:

- **The registration was deleted or edited** in Teams Developer Portal → **Connectors**
  → **OAuth registrations**, changing or invalidating the `referenceId` referenced in
  `manifest.json`.
- **The `referenceId` in `manifest.json` doesn't match** any existing registration
  (e.g. copy/paste error, or the registration was recreated after a tenant migration).
- **The environment ID changed** (e.g. BPA was redeployed to a new Power Platform
  environment) but `manifest.json`'s `mcpServerUrl` was not updated to match.

To recover: verify the registration still exists in Teams Developer Portal, confirm
the `referenceId` in `manifest.json` matches it exactly, or re-run
[`setup-auth.ps1`](README.md#step-6--authentication-required-for-mcp-tools-to-work) to
re-register and re-patch `manifest.json`, then re-upload via **Agents → All agents →
BPA Analytics → Update**.

### Power Platform-side signal

The Power Platform Admin Center does not expose per-request MCP logs to plugin
authors, but you can confirm the environment and role assignment are correct:

- **Power Platform Admin Center** → your environment → **Settings** → **Users +
  permissions** → **Security roles** confirms which users have **BPA User** assigned.
- If a user reports empty results (not an error), this is almost always a missing
  security role or row-level security (RLS) in the underlying BPA dataset, not a
  plugin or auth failure — see [SECURITY.md](SECURITY.md#what-data-the-plugin-can-access).

### Microsoft 365 admin & Copilot usage reports

**M365 Admin Centre** → **Reports** → **Usage** → **Microsoft 365 Copilot** shows
adoption and activity at a tenant level (which users are actively using Copilot).
This doesn't give per-skill or per-tool detail, but it's useful to confirm a user is
actually reaching Copilot at all before assuming the plugin itself is at fault.

## Option B — Local MCP (VS Code)

This is the easiest option to debug because everything runs on the developer's own
machine with visible logs.

- **VS Code Output panel** → select **GitHub Copilot Chat** (or **MCP**, depending on
  VS Code version) from the dropdown — this shows the MCP server connection status,
  handshake errors, and tool call/response payloads.
- **Command Palette** → `MCP: List Servers` — confirms the server is registered and
  its current connection state.
- **Sign-in issues**: run `Azure: Sign In` from the Command Palette. If VS Code's Azure
  AD session has expired or is using the wrong tenant/account,
  `agent365.svc.cloud.microsoft` will reject every call the same way it does in
  Option C.
- **Config errors**: verify `mcp.json` (`%APPDATA%\Code\User\mcp.json` or
  `.vscode/mcp.json`) has the correct environment ID in the URL — a typo here produces
  a connection failure that looks identical to an auth failure.

## Option A — Skills-only

There is no MCP server and no network call in this mode — skills only shape how
Copilot Chat/Agent phrases and routes requests, using whatever BPA access the user's
existing tools already have. If something looks wrong here, the issue is almost always:

- The skill files weren't copied to the expected prompts folder — re-run
  `.\package.ps1 -SkillsOnly` and check the copy step completed.
- The behaviour the user expected actually requires a live MCP connection (Option B or
  C) — Skills-only cannot call any BPA API on its own.

## Escalation checklist

If you've worked through the above and still can't explain a failure, capture the
following before escalating (to Microsoft 365 support, Power Platform support, or the
plugin maintainer):

- [ ] Deployment option in use (A / B / C) and `manifest.json` `version`
- [ ] Exact user prompt and the exact response/error text received
- [ ] Timestamp (with timezone) of the failure
- [ ] Affected user(s) — one user, a subset, or everyone in the tenant
- [ ] Entra ID sign-in log entry for that timestamp, if Option C
- [ ] Whether the Teams Developer Portal OAuth registration still exists and matches
      `manifest.json → referenceId`
- [ ] `manifest.json` `mcpServerUrl` and `authorization.type` (never share the actual
      `referenceId` outside your organisation)
